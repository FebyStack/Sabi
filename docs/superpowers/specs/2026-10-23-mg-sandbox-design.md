# Plan 6 — motion-graphic sandbox: design (2026-10-23)

Spec rows **24–27** (`docs/spec.md`) hold the locked decisions; this document is the how. The owner answered the batch on 2026-10-23: the web edits MG props too; keep the code checks as an early warning; blank until ready, ⚠ after 5 s silent; both extras (agent report + strict editor CSP); defaults for platforms, privacy, exports and integrations. Builder: Opus 5.5, inline. Base: branch `claude/agent-and-ops` (PR #7, on #6).

## Why

An MG's `compiled` code runs today through `new Function` inside Sabi's own pages: the editor (Player), the render page (MP4) and `/frame` stills. In the editor it shares the app's origin, so it can call the API (edit or delete projects, spend fal credits up to the cap), read every transcript on screen, and send any of it anywhere. The only guard is the AST denylist in `backend/modules/mg/compile.ts`, and it can be walked around: `React["createElement"]("iframe")`, a `ref` that climbs `parentNode` to `document`, or a plain `<img src="https://…">` beacon all pass it. Claude writes the MGs and also reads untrusted text (transcripts, web pages, stock metadata), so a prompt injection could plant one.

## Goals, non-goals, anti-goals

- **Goals:** MG code never runs in a Sabi page; inside its sandbox it has no network and no reach into the page; the Player, `/frame` and the MP4 draw MGs identically; a broken MG still draws ⚠; the agent is told why an MG broke or what it was refused; the web edits MG props; the editor page gets a strict CSP.
- **Non-goals:** isolating the render browser's processes (Remotion fixes its Chrome flags), sandboxing anything but MGs, a web code editor, changing what MGs can draw.
- **Anti-goals (a failure even if it works):** a misbehaving MG failing or hanging a render (an endless loop excepted: it still fails after ~40 s); preview ≠ export; `'unsafe-eval'` or inline scripts allowed in the editor; any MG request leaving the machine.

## Probe (2026-10-23, throwaway, scratchpad; Remotion 4.0.536 + its headless shell 157)

- **Frame-exact:** an iframe driven per frame (postMessage + `delayRender` until it answers) gave pixels equal to a plain render on frames 0/15/30/59; the still was exact; 60 frames took 984 ms vs 923 ms plain (+6 %).
- **No network:** 0 of 10 routes reached a canary server (fetch, XHR, WebSocket, sendBeacon, `<img>`, CSS `url()`, stylesheet, prefetch, nested iframe, an about:blank child's fetch). `parent.document` and `localStorage` throw; `origin` is `null`.
- **Navigation:** the iframe navigated itself to the canary (`/nav`) until the page had `frame-src`; with it, 0 hits and a second `load` event on the iframe (detectable).
- **One process:** Remotion launches Chrome with `--disable-site-isolation-trials`, so the iframe shares the page's process; an endless loop still blocks the page.
- **Runtime size:** React + react-dom + Remotion's helpers bundle to ~477 KB minified (149 KB gzip); `remotion` does not tree-shake.

## How it works

### 1. The sandbox document

`frontend/public/mg-sandbox.html`, generated by `npm run build:mg-sandbox` (esbuild: IIFE, minified, `NODE_ENV=production`, no legal comments) from `shared/remotion/sandbox/entry.tsx`, committed. A unit test rebuilds it in memory and fails when the committed file is stale. Vite serves it at `/mg-sandbox.html` (dev and build, so nginx too); the renderer bundles with `publicDir: frontend/public`, so Remotion's bundle server serves it as well. `staticFile("mg-sandbox.html")` gives the right URL in both (`/mg-sandbox.html` in the Player, `<staticBase>/mg-sandbox.html` in renders).

A real file, not `srcdoc`: a `srcdoc` (or blob/data) document inherits the embedding page's CSP, and the strict editor CSP forbids inline scripts and eval, which the sandbox needs. A same-origin file loaded into `sandbox="allow-scripts"` gets an opaque origin and only its own policy:

```
default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval'; style-src 'unsafe-inline'; img-src blob: data:; font-src blob: data:; base-uri 'none'; form-action 'none'
```

The document: `<html lang="en">` (as the render page), `body { margin: 0 }`, transparent background, one inline `<script>` with the runtime. Unstyled text is the browser default, as in today's export.

### 2. The runtime inside (`entry.tsx` + `shared/remotion/mgRuntime.ts`)

`mgRuntime.ts` keeps today's MG code path, now used only inside the sandbox:

- `MG_SCOPE` = `React, AbsoluteFill, Img, Easing, interpolate, interpolateColors, random, spring, useCurrentFrame, useVideoConfig`. `AbsoluteFill`, `Easing`, `interpolate*`, `random`, `spring` are Remotion's own. `useCurrentFrame()` returns the MG's local frame and `useVideoConfig()` returns `{ id: "CaptionVideo", width, height (the frame), fps, durationInFrames (the MG's) }` from a context. `Img` maps a known URL to its blob URL, tracks loading, and draws `⚠ image` (and reports it) on error.
- `buildMotionGraphic(compiled)` is unchanged (`new Function` with the scope; `MgBroken` on an evaluation error or no `Component`).
- `MgView` = root `div` (`position: absolute; inset: 0; overflow: hidden`) → `MgBoundary` (⚠ `mg-<n>` on a render error, reports `threw`) → `Component`; `frame: null` renders nothing.

`entry.tsx` runs the message loop. On `init` it builds the `@font-face` rules from the fonts payload with blob URLs, makes blob URLs for the image Blobs (decoded before `ready`), and builds the component. On `draw` it renders with `flushSync`, waits for pending `<Img>` loads and `document.fonts.ready`, then answers `drawn`. A `securitypolicyviolation` listener reports `blocked`. It accepts messages only from `parent` and captures `parent` at startup.

### 3. The host (parent: `shared/remotion/MotionGraphicLayer.tsx`)

Per MG, for the whole composition (not only inside its range, so it never boots mid-playback):

- One `<iframe>` in the box: `src = staticFile("mg-sandbox.html")`, `sandbox="allow-scripts"` (no same-origin, forms, popups, top navigation or downloads) everywhere: the attribute sandboxes every document the frame ever holds, so a navigation can't land unsandboxed at Sabi's origin. In the editor the page also arrives with `Content-Security-Policy: sandbox allow-scripts; frame-ancestors 'self'` (Vite, nginx), and its first statement throws unless its origin is opaque. The Claude desktop browser pane cancels loads of frames that carry the attribute, so MGs show ⚠ there; regular browsers draw them (found in the execution check; header-only sandboxing was tried and dropped after a security review). Then `title = mg.id`, `aria-hidden`, `tabIndex = -1`, style `position: absolute; left/top/width/height` = box in px, `border: 0`, `pointer-events: none`, `color-scheme: normal` (otherwise Chrome paints an opaque canvas under the editor's dark scheme), `visibility: hidden` outside the MG's range.
- Keyed on `compiled` + its image URLs + the logo URL: new code or a new image re-creates the sandbox (a fixed MG drops its ⚠, as today).
- Its window (`from = msToFrames(startMs)`, duration, local frame) is computed directly; `<Sequence>` is gone.
- **Handshake:** on the iframe's first `load` the host posts `init { compiled, fps, width, height, fonts, images }`. The sandbox answers `ready`; then, while the MG is in range, each frame is posted as `draw { seq, frame, item }` and answered `drawn { seq }`. Leaving the range posts one `draw { frame: null }` so a stale frame never flashes on re-entry.
- **Renders** (`getRemotionEnvironment().isRendering`): one `delayRender` from mount until `ready`, and one per `draw` until `drawn`. **Player:** no waits; up to one frame behind while playing, exact when paused.
- **Dead:** no `ready` within 15 s, no `drawn` within 5 s, or a second `load` (the MG tried to navigate; the page's `frame-src` blocked it). The iframe is removed, the box shows the existing `MgPlaceholder` (`⚠ mg-<n>`) while in range, waits are released, and `silent` or `navigated` is reported.
- **Fonts payload** (once per page, cached): every `@font-face` rule of the six bundled CSS families (`fontCssFamily`) in the page's same-origin stylesheets, with each `url()` fetched as a Blob and replaced by an index. That is ~690 KB for all subsets, read from the page's own server.
- **Images:** `MotionGraphicProps.images` (new; the MG's image-prop URLs, from `motionGraphicTimeline`) plus `brand.logoUrl`, each fetched once per page as a Blob. A failed fetch is reported `image` and the URL is sent unchanged, so the sandbox blocks it and `<Img>` draws `⚠ image`.
- **Messages from the sandbox** are accepted only from its own `contentWindow`, only the three known types, and details are cut to 200 characters.

### 4. Pages

- **Render page:** `shared/remotion/index.ts` adds `<meta http-equiv="Content-Security-Policy" content="frame-src 'self'">` to the head before `registerRoot`, so a sandbox can't navigate off the bundle server.
- **Editor:** a Vite plugin (`transformIndexHtml`, `order: "post"`, dev and build) puts this meta first in `<head>`:

  ```
  default-src 'self'; script-src 'self' <sha256 of each inline script>; style-src 'self' 'unsafe-inline';
  img-src 'self' blob: data:; media-src 'self' blob:; font-src 'self' data:;
  connect-src 'self' [ws: wss: in dev] [the PostHog origin when VITE_POSTHOG_HOST is set];
  frame-src 'self'; worker-src 'self' blob:; object-src 'none'; base-uri 'none'; form-action 'self'
  ```

  The only inline script is plugin-react's dev preamble, so it gets its hash; the build has none. `'unsafe-inline'` for styles covers Vite's dev CSS and the Player's style tags. No `'unsafe-eval'` anywhere, because MG code no longer runs here. `frame-ancestors 'self'` (header only) goes in Vite `server.headers`/`preview.headers` and nginx `add_header`. `'self'` also allows the sandbox file to be framed, and still blocks other sites from framing the editor.

### 5. Problem report (row 26)

Kinds: `threw` (evaluation error, no `Component`, render error: the message), `image` (an image or logo failed: the URL), `blocked` (a CSP violation: directive and URL), `navigated`, `silent` (not started in 15 s / no answer in 5 s). The host logs each one once per page as `console.warn("sabi:mg " + JSON.stringify({ mg, kind, detail }))`. `RemotionRenderer.renderStill` collects those lines through Remotion's `onBrowserLog` and returns `{ mgProblems }`. `GET /frame` sends them in header `x-sabi-mg-problems`: JSON, at most 10, ASCII-escaped. The MCP client parses the header and `render_frame` adds one line per problem with a hint, e.g. `mg-0 blocked img-src https://images.pexels.com/… — MG images come only from image props or item.brand.logoUrl`. Nothing is stored. The MP4 render ignores them.

### 6. Web props editor (row 25)

Each MG row in the B-roll panel gets **Edit** when it has props. It opens a `Sheet` titled with the MG's name, with one field per prop and a label from its key (`unitLabel` → "Unit label"):

- text: input, ≤ 500 characters
- number: number input
- colour: `<input type="color">`, `#rrggbb`
- boolean: `Switch`
- image: thumbnail + Replace (upload PNG/JPEG/WebP → asset id)

Text, number and colour commit after 300 ms (`useDebouncedCommit`); the rest commit at once. Every commit is `updateMotionGraphic { mgId, props }` with the whole array, and the sheet keeps a draft so a pending change survives the next one. `bad_asset` and upload errors show as a `Notice`. Undo uses the existing inverse (the old props). Props stay a server-side fold: the Player updates after the commit (~0.5 s).

### 7. Code checks (row 25)

`compileMotionGraphic` is unchanged. Its header comment and `motion-graphics.md` call it the agent's early warning; the sandbox is the boundary.

### 8. What changes for MG authors (`motion-graphics.md`)

- The MG runs sandboxed: no network, no access to Sabi's page.
- Images come only from image props and `item.brand.logoUrl`; anything else is blocked and reported.
- `useVideoConfig()` is `{ id, width, height, fps, durationInFrames }`; the whole composition's props (the transcript) are gone.
- Text without a font is the browser default (serif) in preview and export alike. Today the Player inherited the editor's font, so always set `fontFamily` from `item.brand`.
- `render_frame` lists each MG's problems.
- An MG that stops answering for 5 s shows ⚠; an endless loop still fails the render after ~40 s.

## Blueprint

- **Folder structure:**
  - `shared/remotion/sandbox/entry.tsx`: sandbox message loop.
  - `shared/remotion/mgRuntime.ts`: sandbox-side scope, build, view (moved logic).
  - `shared/remotion/mgHost.ts`: parent-side protocol types, fonts and images payloads, problem log.
  - `shared/remotion/MotionGraphicLayer.tsx`: the host.
  - `infrastructure/dev/build-mg-sandbox.ts`: build script, also imported by its freshness test.
  - `frontend/public/mg-sandbox.html`: generated.
  - `infrastructure/dev/editorCsp.ts`: the policy, used by `vite.config.ts`.
  - `frontend/src/features/editor/panels/MgPropsSheet.tsx`.
  - Also touched: `backend/shared/renderer.ts`, `backend/modules/frames/routes.ts`, `backend/mcp/{client,tools}.ts`, `infrastructure/docker/{Dockerfile,nginx.conf}`, docs.
- **Component architecture:** `CaptionVideo` → `MotionGraphicLayer` (window, key) → iframe or `MgPlaceholder` → [sandbox] `entry.tsx` → `MgView` → `MgBoundary` → agent `Component`. Layer order is unchanged: footage → B-roll → tint → MGs → captions.
- **Design system:** no new tokens. The props sheet reuses `Sheet`, `Field`, `Switch`, `Button` and `Notice`; the ⚠ placeholders are unchanged.
- **Responsive:** iframes scale with the Player's composition transform. The props sheet is the existing bottom sheet with 44 px targets. Checked at 375 px and on desktop.
- **State management:** the host phase per MG (`booting → ready → dead`) lives in component state. Module caches hold the fonts payload, image Blobs per URL and the problems already logged. No new store.
- **Performance:**
  - Per MG, parsing the ~480 KB runtime and the font rules. One ~690 KB font fetch per page that shows MGs.
  - Renders ≈ +6 % in the probe. Budget ≤ +20 % on the demo export, measured in the plan.
  - All of a composition's MG iframes mount up front. Lazy mounting is a follow-up if projects grow many MGs.
- **SEO:** n/a (noindex app). **Analytics:** no new events, and MGs can't send any.
- **Accessibility:** sandbox iframes are hidden from assistive tech and focus. Props fields are labelled.
- **Deployment:**
  - Docker's api stage copies `frontend/public`, since the renderer bundles it.
  - nginx sends `frame-ancestors`.
  - CI runs the freshness test inside `npm run verify`.
  - No DB migration.
- **Testing:**
  - Unit (vitest, node): the sandbox view through `renderToStaticMarkup`, protocol and watchdog with fake timers, both CSPs, the font-rule rewrite, image lists, the problems header and `render_frame` text, the props sheet.
  - Gated render tests (`render:sample`):
    - a network canary across every route, including navigation
    - frame-exact colours
    - still = MP4
    - an image prop drawn from bytes
    - throw ⚠, image ⚠, silent ⚠, navigation ⚠
    - an endless loop still fails
    - the problem report
  - Manual (browser pane):
    - the demo's MG in the Player vs `/frame`
    - the props sheet at 375 px
    - an editor console free of CSP violations

## Trade-offs

| Choice | Over | Because | Cost |
|---|---|---|---|
| One sandboxed iframe per MG | one iframe for all MGs; SES/QuickJS realms; rendering sanitized markup in the page | browser-enforced isolation, exact pixels, ⚠ and reports per MG | ~480 KB runtime parsed per MG |
| A real file document | `srcdoc` | `srcdoc` inherits the editor's strict CSP (no inline script, no eval) | the renderer needs `publicDir`; Docker copies `frontend/public` |
| Fonts and images as bytes | letting the sandbox fetch | zero network inside; no CORS dependence on the sandbox's `null` origin | ~690 KB font read per page; the page fetches image props itself |
| Committed generated file + freshness test | building it in Vite, the API and Docker | one artifact every entry point already serves | a ~480 KB generated file in git |
| Renders wait, the Player doesn't | waiting everywhere | exact export, smooth preview | ≤ 1 frame lag while playing |
| Watchdog 5 s per frame, 15 s to start | no watchdog | a broken runtime draws ⚠ instead of failing the render | ⚠ can be timing-dependent for pathological MGs |
| Keep the denylist | removing it | the agent gets a clear 400 instead of a silent failure | false positives stay (`top`, `open`…) |
| Report via console → `onBrowserLog` → header | a new endpoint or storage | the still already runs in that browser; nothing stored | only `render_frame` reports, not the MP4 render |

## Residual risks

- **Endless loop.** It fails the render after ~40 s (one process). In the Player it freezes the tab unless the browser gives the sandbox its own process.
- **Side channels.** DNS, WebRTC or preconnect-style channels could leak an MG's own inputs (its props, the brand), which is all the sandbox holds. Same-process side channels (Spectre-class) exist in renders, because Remotion turns site isolation off.
- **iOS Safari.** Whether WebKit applies the page's `frame-src` to an iframe's own navigation is unverified. Worst case is a beacon carrying the MG's inputs.
- **CPU or memory exhaustion** by an MG slows or crashes its tab or render.
